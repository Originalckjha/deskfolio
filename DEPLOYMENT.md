# Deploying DeskFolio

Three services, set up in this order: **MongoDB Atlas** (database), then **Render** (API), then **Vercel** (web app).
Each needs a value from the one before it. All three have free tiers that are enough to launch.

Before you start, push this folder to a GitHub repository (Render and Vercel deploy from Git).
`.gitignore` already keeps `.env` files and `node_modules` out.

---

## 1. MongoDB Atlas

1. Create a free **M0** cluster at <https://cloud.mongodb.com>. Pick the region closest to your Render region
   (Render's `singapore` pairs well with AWS `ap-southeast-1` or `ap-south-1` Mumbai).
2. **Database Access** → *Add New Database User* → password auth. Give it **Read and write to any database**
   (or scope it to the `deskfolio` database). Use a generated password with no `@ : / ?` characters,
   or URL-encode it.
3. **Network Access** → *Add IP Address* → `0.0.0.0/0`.
   Render's free tier has no fixed outbound IP, so Atlas has to accept any address. The username and password
   still protect the database. On a paid Render plan you can list Render's static outbound IPs instead.
4. **Connect** → *Drivers* → copy the connection string and add the database name before the `?`:

   ```
   mongodb+srv://<user>:<password>@<cluster>.mongodb.net/deskfolio?retryWrites=true&w=majority
   ```

   This is your `MONGODB_URI`.

You don't need to create collections or indexes by hand. The Render build runs `npm run db:indexes`, which
creates every index, including the unique ones the app relies on (one enrollment per student per space, one
rating per student per educator). It's safe to run repeatedly.

## 2. Cloudinary (file uploads)

1. Sign up at <https://cloudinary.com> and open the dashboard.
2. Copy **Cloud name**, **API key** and **API secret**.
3. Recommended: *Settings → Security* → make sure **"PDF and ZIP files delivery"** is allowed. DeskFolio uploads
   PDFs and slides as `raw` files, but some accounts still restrict them.

Without these keys the API still runs; only file uploads return "not configured".

## 3. Render (API)

The repo includes [`render.yaml`](render.yaml), a Render Blueprint.

1. Render dashboard → **New → Blueprint** → connect your repo. Render finds `render.yaml` and proposes the
   `deskfolio-api` service.
2. Fill in the values it asks for:

   | Variable | Value |
   | --- | --- |
   | `MONGODB_URI` | the Atlas string from step 1 |
   | `CLIENT_ORIGINS` | your Vercel URL, e.g. `https://deskfolio.vercel.app`. Add previews with a wildcard: `https://deskfolio.vercel.app,https://deskfolio-*-yourteam.vercel.app` |
   | `CLOUDINARY_*` | the three values from step 2 |

   `JWT_SECRET` is generated by Render automatically. `PORT` is set by Render; don't add it.
3. Deploy. The build runs `npm ci --omit=dev && npm run db:indexes`, then starts `npm start`.
   The build log lists every index it created, which is a good sign Atlas is reachable.
4. Check it: open `https://<your-service>.onrender.com/api/health`. It should return
   `{"status":"ok","db":"up",...}`. Render also uses this path as its health check.

If you don't know the Vercel URL yet, put a placeholder in `CLIENT_ORIGINS`, deploy Vercel, then come back and
update it. Render redeploys when an env var changes.

**Free-tier sleep:** free Render services sleep after about 15 minutes idle, and the next request takes
30–60 seconds while it wakes. The web app waits up to 60 s per request, so it works, just slowly at first.
A paid instance (or an uptime pinger on `/api/health`) avoids this.

## 4. Vercel (web app)

1. Vercel dashboard → **Add New → Project** → import the repo.
2. Set **Root Directory** to `client`. Vercel reads [`client/vercel.json`](client/vercel.json)
   (Vite build, output `dist`).
3. Add the environment variable:

   | Variable | Value |
   | --- | --- |
   | `VITE_API_URL` | `https://<your-service>.onrender.com/api/v1` |

   `VITE_` variables are baked in at build time, so redeploy after changing it.
4. Deploy, then copy the production URL back into Render's `CLIENT_ORIGINS` if you haven't already.

What `vercel.json` does:

- **SPA routing:** every path except `/assets/*` and the favicon serves `index.html`, so deep links like
  `/e/rahul-sharma-physics` or `/read/<id>` work on refresh.
- **Caching:** hashed files in `/assets` are cached for a year.
- **Security headers:** `nosniff`, `X-Frame-Options: DENY`, a strict referrer policy, and a Content Security Policy.
  The CSP allows API calls only to `https://*.onrender.com`. **If you put the API on a custom domain,
  add it to `connect-src`** in `client/vercel.json`, or every API call will be blocked.

## 5. After the first deploy

- [ ] `/api/health` returns `ok` / `db: up`
- [ ] The Vercel site loads the landing page and leaderboard with no console errors
- [ ] Register an educator, create a space, add a note, upload a small PDF
- [ ] In a private window, register a student, join with the code, open the note, rate the educator
- [ ] The rating appears on the leaderboard

If the browser console shows a **CORS** error, `CLIENT_ORIGINS` on Render doesn't exactly match the site's
origin (scheme + host, no trailing slash). If it shows a **Content Security Policy** error, see the
`connect-src` note above.

## Optional: custom domains

- Vercel: *Project → Settings → Domains*, e.g. `deskfolio.app`.
- Render: *Service → Settings → Custom Domains*, e.g. `api.deskfolio.app`.
- Then update `CLIENT_ORIGINS` (Render), `VITE_API_URL` (Vercel, redeploy) and `connect-src` in `client/vercel.json`.
